Field notes

Git cheat sheet

Eleven ideas that keep a project honest: what each one does, when it bites, and how it looks in motion.

Repository Clone Branch Commit Push / Pull Diff Merge Rebase Merge conflict Pull Request Issue

01

Repository (repo)

The project folder, tracked by Git and hosted on GitHub and friends.

What it does

A repository is the unit Git cares about: a working tree plus a hidden .git directory that stores every snapshot, branch, and remote. Locally it is just a folder. Remotely it is the shared source of truth teammates clone, push to, and review.

Considerations

  • Initialize once at the project root, not inside nested copies of the same app.
  • Keep secrets out of history with .gitignore from the first commit.
  • One repo per product is simpler than a monorepo unless you already need shared versioning.

Resources

  • Pro Git: Getting a Git Repository
  • GitHub Docs: Repositories

02

Clone

Download a copy of the code to your machine.

What it does

Cloning copies the entire repository history, not just the latest files. You get a local main (or default) branch, a remote named origin, and a working tree you can edit without touching anyone else’s machine.

Considerations

  • Clone the HTTPS or SSH URL from the host; SSH is nicer once keys are set up.
  • A shallow clone (--depth 1) is faster but hides history you may need for blame or rebase.
  • After cloning, you still need to pull to stay current.

Resources

  • git-clone documentation
  • Cloning a repository on GitHub

03

Branch

A safe parallel timeline to the main codebase.

What it does

A branch is a movable pointer to a commit. Creating one lets you experiment, ship a feature, or fix a bug without rewriting main until you are ready. Everyone else can keep working on their own pointers at the same time.

Considerations

  • Name branches by intent: fix/login-timeout, not ceci-wip-2.
  • Short-lived branches merge cleaner than weeks-long ones.
  • Delete the branch after it lands so the graph stays readable.

Resources

  • Pro Git: Branches in a Nutshell
  • GitHub: About branches

04

Commit

A snapshot plus a message describing your changes.

What it does

A commit freezes the staged files, records who made the change and when, and points at its parent commit. The message is the human interface to that snapshot: future you (and reviewers) will read it more often than the diff.

Considerations

  • Commit focused units of work, not an entire afternoon of unrelated edits.
  • Write the subject in the imperative: “Add login timeout”, not “Added stuff”.
  • Avoid --amend and rebases on commits already pushed to a shared branch.

Resources

  • git-commit documentation
  • Conventional Commits

05

Push / Pull

Upload to, or download from, the hosted repository.

What it does

git push sends your local commits to a remote branch. git pull fetches new commits from that remote and integrates them into your current branch (fetch + merge, or fetch + rebase if you configure it that way).

Considerations

  • Pull before you push on a shared branch so you do not overwrite teammates.
  • Never force-push to main; if you must rewrite a feature branch, coordinate first.
  • pull --rebase keeps a linear history but rewrites your local commits.

Resources

  • git-push documentation
  • git-pull documentation

06

Diff

The visual difference between two versions of the code.

What it does

A diff shows what was added, removed, or changed between commits, branches, or your working tree and the index. GitHub pull requests are built on the same idea: a structured, reviewable delta instead of “trust me, it works.”

Considerations

  • Whitespace-only diffs hide real changes; enable ignore-whitespace when hunting logic bugs.
  • Binary files (images, lockfile noise) make diffs painful; generate them deliberately.
  • Review the diff, not just the file list: context lines tell you if a rename is safe.

Resources

  • git-diff documentation
  • Comparing branches in pull requests

07

Merge

Combine a branch back into another branch.

What it does

A merge joins two histories. A fast-forward just moves the pointer forward when nothing diverged. A true merge creates a new commit with two parents, preserving the fact that work happened in parallel.

Considerations

  • Merge main into your feature branch first if it has moved, then merge the feature in.
  • Merge commits are honest about chronology; some teams prefer rebase for a straight line.
  • Never merge with unresolved conflict markers still in the files.

Resources

  • git-merge documentation
  • Atlassian: git merge

08

Rebase

Replay your commits on top of the latest main.

What it does

Rebase takes each commit on your branch and reapplies it, in order, onto another tip—usually updated main. The result looks as if you started from today’s main all along. The original commits are replaced with new hashes.

Considerations

  • Rebase local or private branches; rewriting shared history forces everyone else to recover.
  • Conflicts can appear once per replayed commit, not all at once like a merge.
  • Use rebase -i to squash or reword before you open a pull request, not after review starts.

Resources

  • Pro Git: Rebasing
  • git-rebase documentation

09

Merge conflict

Two changes touched the same lines; you choose.

What it does

Git can auto-merge files that changed in different places. When both sides edited the same hunk, it stops and marks the file with conflict markers. You pick one side, the other, or a blend, then commit the resolution.

Considerations

  • Read both sides and the surrounding code; “accept incoming” is not always correct.
  • Search the tree for leftover <<<<<<< markers before you commit.
  • Talk to the other author when the intent is unclear—conflicts are a conversation, not a quiz.

Resources

  • Pro Git: Basic merge conflicts
  • GitHub: Addressing merge conflicts

10

Pull Request (PR)

“Please review and merge my branch.”

What it does

A pull request (or merge request) is the social layer on top of a branch: a diff, a description, reviewers, CI checks, and a recorded decision to merge. Git itself does not require PRs; GitHub, GitLab, and similar hosts do.

Considerations

  • Keep PRs small enough to review in one sitting.
  • Describe why, not only what; link the issue you are closing.
  • Do not merge on red checks unless you understand the failure.

Resources

  • GitHub: About pull requests
  • GitHub Docs: Pull requests

11

Issue

A ticket: bug, feature, or task.

What it does

An issue tracks work that is not (yet) a branch. It captures the problem, acceptance criteria, and conversation. Good issues become the description of a later pull request; they also give you a number to reference in commit messages.

Considerations

  • Write reproduction steps for bugs; write the user outcome for features.
  • One issue, one outcome—split “redesign the app” into smaller tickets.
  • Close issues from the PR (Closes #17) so the paper trail stays attached to the code.

Resources

  • GitHub: About issues
  • GitHub Docs: Issues
